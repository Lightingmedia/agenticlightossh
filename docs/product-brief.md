# Aurora Fabric OS / LightOS — product brief

LightRail AI is the company. Aurora Fabric OS is the agentic infrastructure product. LightOS is its workspace.

The intended loop is **intent → verified capacity → policy/budget checks → plan → approval → supported execution → verified outcome**. Dashboards display agent state and real infrastructure measurements; they do not replace the agent thesis.

LightOS manages infrastructure a customer already owns or rents. It is not a GPU cloud, a replacement for Ubuntu, or a chip product. GPU rental is billed separately by the compute provider.

## Current offer

Early-access provider/GPU monitoring and agent planning. Credential validation and inventory paths exist; a catalog entry does not prove every provider or operation works. Real telemetry requires a reachable runtime gateway on a GPU host.

The gateway supports bounded inference jobs with a configured model server. Full intent/approval/execution/read-back and paid access need signed-in end-to-end verification before being sold as operational.

Free: one GPU, monitoring only, no card required. A second GPU triggers an upgrade. Server-side entitlement and workspace isolation are launch gates; hiding UI cards is not enforcement.

## How the parts relate

- MCP: agent tools.
- MTMC: intent/model routing, not a cluster executor.
- Gateway: the sole privileged execution boundary; no host or gateway credentials in the browser.
- Provider connections: access to supported customer-owned compute accounts.
- Dashboard: inspection, approval, status, telemetry, and audit views.
- Browser desktop/terminal: workspace and simulated shell, not a real host OS.
- Photonic fabric, broad accelerator translation, silicon, RISC-V: retained research/roadmap work, not launch guarantees.

## Rules for another AI

1. Preserve the agent-first thesis and build one real closed loop before more apps.
2. Distinguish implemented source, deployed capability, and verified customer results.
3. Missing hardware is unavailable; synthetic output is demo, never live success.
4. No SOC 2, utilization, universal execution, or savings claims without evidence.
5. Privileged actions need authorization, permitted actions, bounded budgets, approval, and audit records. Generated text is never unrestricted shell execution.
6. No training on customer prompts/telemetry by default without consent and policy.
7. Apply free monitoring and paid execution rules equally to web, MCP, and gateway access.

## Launch gates

Three pilot teams reach a verified result; one signed-in user completes a real supported job loop; accounts are isolated; free users cannot bypass entitlements; live payment/cancellation/webhooks update access; legal, support, rollback, and versioned distribution are ready. Dates never override these gates.
